# 관계 추론 확장 검증 보고서

작성일: 2026-10-03

기존 진단 앞에 사실 추출, 고정 SPARQL 규칙, SHACL 검사와 LLM 문맥 구성을 연결했다. 원본 백엔드 입력과 공개 `diagnosis-result.v3` 형식은 유지하며 로그 1회와 조건부 소스 1회의 기존 모델 호출 흐름을 사용한다. 활성화 설정과 지원 문법은 [관계 추론 개발 문서](RELATION_REASONING.md)에 정리했다.

## 구현 범위

세 규칙군을 다섯 쿼리로 구현했다. 포트 차이와 직접 probe 실패, 같은 작업의 실패 후 복구, 설정 계약과 코드 참조 및 실행 오류의 연결을 처리한다. 사실과 파생 관계, LLM의 주장을 분리하고 원인 후보에는 전제와 미확인 사항을 남긴다. 확인되지 않은 프로세스 식별이나 포트 매핑을 추측하지 않는다.

입력 문법을 인식하지 못하면 기존 LLM 분석을 유지한다. Python 소스는 직접적인 환경변수 참조부터 지원하며, 부분 코드·동적 키·환경변수 별칭·재정의는 보수적으로 제외한다. 이 구현이 모든 IRIS 로그 형식과 언어를 처리한다는 의미는 아니다.

## 기능과 배포 검증

- 전체 테스트 345개 통과, Ruff와 의존성 일관성 검사 통과.
- 추론 off에서 모델 입력·프롬프트 동일성, off와 assist의 OpenAPI 동일성, 공개 v3 응답 검증.
- EV·SC 추적, 다른 대상·배포 시도·시간 범위, 다중 리스너·매핑·상충 스냅샷, 복구 뒤 재실패, 설정 별칭 반례 검사.
- 로그·소스 두 단계 연결과 호출 상한, 추론 시간 초과·슬롯 부족·취소·100회 뒤 교체·정상 종료 검사.
- wheel에 다섯 SPARQL 쿼리, 온톨로지·shapes와 worker 포함 확인.
- Docker 이미지 `iris-error-check-agent:relation-assist` 빌드 성공. 네트워크 없는 컨테이너에서 UID 10001로 worker 재사용, SHACL 적합, 추론 기록과 파일 권한 0600, 종료 확인.

Docker 검증 결과는 `results/reasoning-docker-smoke.json`에 보관했다. 기존 비동기 저장은 정상 종료 시 완료를 기다리지만 강제 종료 시 영속성을 보장하는 큐는 아니다.

## 규칙 평가

개발용 24건과 시험용 60건을 별도 파일로 작성했다. 시험용은 관계 기반 장애 24건, 반례 12건, 정상·복구 12건, 정보 부족 12건이다. 사례 생성 시 관계 종류와 EV·SC 정답을 정의하며 생성 그래프를 정답으로 복사하지 않았다.

시험용 60건에서 정의한 파생 관계 72개와 근거 연결이 모두 일치했다. 해당 범위에서 TP 72, FP 0, FN 0이며 precision·recall·F1은 각각 1.0이다. 이는 지원 문법과 규칙군을 공유하는 작성된 합성 사례의 결과다. 전체 온톨로지 엣지 정확도나 LLM 원인 정확도, 운영 장애 정확도로 해석하지 않는다.

## 추론 시간과 자원

macOS arm64, Python 3.12.14에서 실제 추론 subprocess를 사용했다. 예열 후 40회 단일 요청과 별도의 동시 요청 묶음을 측정했다. 모델 호출과 인터넷 시간은 제외한다.

| 항목 | 측정값 |
|---|---:|
| 작은 그래프 크기 | 49트리플 |
| 작은 그래프 p50 / p95 | 약 3.65 / 4.12ms |
| 확장 그래프 크기 | 294트리플 |
| 확장 그래프 p50 / p95 | 약 26.13 / 27.63ms |
| 확장 측정의 프로세스 예열 | 약 215ms |
| 확장 측정의 worker 최대 RSS | 약 48.9MiB |
| 확장 측정 전체 worker CPU | 약 1.80초 |

CPU는 예열과 성공한 64개 추론 작업을 포함한 전체 측정 프로세스 사용량이다. 요청당 CPU 또는 운영 서버 평균값이 아니다. 데이터 파일은 `results/reasoning-benchmark.json`, `results/reasoning-benchmark-294.json`이다. 첫 작은 그래프 측정 후 상충 스냅샷 방어 조건과 구현 해시 기록을 추가했고, 확장 그래프와 Docker 측정은 최종 규칙으로 수행했다. 서로 다른 크기의 결과를 직접 속도 개선율로 비교하지 않는다.

worker 1개에서 동시 2개 요청을 8회 보냈을 때 8개는 추론을 수행하고 8개는 busy로 기존 진단 경로를 사용했다. 동시 4개 요청은 8개 수행·24개 busy였다. 이때 빠르게 반환한 busy를 성공한 추론 지연으로 해석하면 안 된다. 실제 서비스의 도착 간격과 동시성에 따른 적용률은 별도 운영 측정이 필요하다.

## 실제 모델 비교 방법

동일한 백엔드 입력·아카이브와 모델 설정으로 기존 방식, 그래프 사실 제공, 그래프 규칙 추론을 독립 호출했다. 사실 제공군은 파생 규칙을 실행하지 않는다. 각 비교군의 실제 프롬프트·입력·스키마·응답, 공개 진단, 그래프와 추론 기록을 저장한다. 규칙 결과는 기존 원문을 대체하지 않으며 토큰과 소스 선택 차이도 기록한다.

소규모 개발 검증은 3건 × 3개 비교군, 실제 호출 12회였다. 상태 점수는 세 비교군 모두 3/3, 사전 원인 채점은 기존 2/3·사실 2/3·규칙 3/3이었다. 연결 검증용 작은 표본이며 효과 추정치로 사용하지 않는다. 저장 위치는 `results/relation-live-smoke`다.

시험용 전체 비교는 `results/relation-live-test-60`에 보관한다. 최종 수치는 아래 자동 집계 표와 함께 해석한다.

| 지표 | 기존 방식 | 사실 제공 | 규칙 추론 |
|---|---:|---:|---:|
| 상태 정확도 | 60/60 (100.0%) | 60/60 (100.0%) | 59/60 (98.3%) |
| 원인 식별 사전 채점 | 23/24 (95.8%) | 22/24 (91.7%) | 19/24 (79.2%) |
| 핵심 근거 연결 | 24/24 (100.0%) | 24/24 (100.0%) | 23/24 (95.8%) |
| 정상·복구 오탐 | 0/24 (0.0%) | 0/24 (0.0%) | 0/24 (0.0%) |
| 정보 부족 단정 | 0/12 (0.0%) | 0/12 (0.0%) | 0/12 (0.0%) |
| 실행 오류 | 0 | 0 | 1 |
| 모델 요청 제출 | 72 | 72 | 72 |
| 확인된 제공자 호출 | 72 | 72 | 71 |

모델은 기존 설정의 `gpt-6.1-sol`을 사용했다. 사례·비교군 조합 180개를 완료했으며 모델 요청은 총 216회 제출했다. 응답으로 확인한 제공자 호출은 215회이고 규칙군 test-001의 `MODEL_ERROR` 1건은 제공자 처리 여부·토큰을 확정하지 못했다. 해당 실행을 분모에서 빼거나 재시도하지 않았다. 이 오류의 구체적인 제공자 HTTP 상태는 저장되지 않아 원인을 더 좁히지 않았다.

규칙군의 원인 채점 미통과 5건은 실행 오류 1건과 원인 표현 정규식 미통과 4건이다. 기존군의 1건과 사실군의 2건도 표현 검사에서만 미통과했다. 실행된 답변의 분류와 핵심 근거는 이 미통과 사례들에서도 맞았다. 원인 점수의 차이를 그대로 실제 의미 정확도의 하락 또는 향상으로 해석하지 않는다.

사실군과 규칙군은 각각 72단계 중 67단계에 내부 문맥을 전달했다. 나머지 5단계는 추출 사실이 없어 기존 문맥을 사용했으며 시간 초과·busy·worker 오류로 인한 생략은 없었다. 규칙 후보는 42단계에 전달됐다. 이는 모델에 제공한 비율이며 후보 채택률이 아니다. 두 비교군의 기록에서 각각 하나의 구현 해시 집합을 확인했다.

| 확인된 사용량 | 기존 방식 | 사실 제공 | 규칙 추론 |
|---|---:|---:|---:|
| 입력 토큰 | 457,986 | 483,687 | 486,099 |
| 출력 토큰 | 90,472 | 90,366 | 89,811 |

전체 비교의 확인된 입력·출력 토큰 합계는 1,698,421이다. 출력에 포함된 reasoning 토큰은 다시 합산하지 않았다. 규칙군의 실패한 요청 1건은 사용량이 누락되어 실제 총 청구량과 같다고 보장할 수 없으며 금액 비용은 산출하지 않았다. 연결 검증용 12회 호출의 사용량은 별도 smoke 요약에 남겨 전체 비교와 섞지 않았다.

HTTP 응답 중앙값은 기존 약 16.94초, 사실 약 16.81초, 규칙 약 16.84초였고 p95는 각각 약 57.09초·56.62초·56.65초였다. 서로 다른 모델 출력과 외부 서비스 변동, 병렬 실행이 포함된 값이므로 추론으로 속도가 개선됐다고 해석하지 않는다.

사전 채점의 기존→규칙 대응 결과는 둘 다 통과 19건, 기존만 통과 4건, 둘 다 미통과 1건이다. 사실→규칙은 둘 다 통과 18건, 사실만 4건, 규칙만 1건, 둘 다 미통과 1건이다. 상세 분모·Wilson 참고 구간과 미통과 문장은 `comparison.json`에 보관했다. 이번 평가에서는 계획한 원인 점수 +10%p 도입 기준을 충족하지 못했다.

## 점수 해석과 도입 판단

사전 원인 채점은 최상위 분류, 표현 정규식, 핵심 근거를 모두 요구한다. 예를 들어 test-001의 기존 모델은 “대상 포트 8080과 실제 유일한 수신 포트 3000이 일치하지 않아” 연결이 거부됐다고 설명했지만, 고정 표현 목록에 `일치하지`가 없어 원인 점수에서 탈락했다. test-021·022의 규칙 적용 답변에도 같은 종류의 표현 미포함이 있었다. 사후에 정규식을 넓혀 점수를 올리지 않았다.

따라서 원인 점수는 규칙 기반 대리 지표다. 자유 서술의 의미 정확도를 확인하려면 비교군을 가린 사람 검토가 추가로 필요하며 이번 작업에서 완료됐다고 주장하지 않는다. 사례가 비슷한 규칙군과 템플릿을 공유하므로 통계 구간 역시 독립적인 운영 장애 표본에 대한 신뢰구간이 아니다.

현재 공개 기본값은 `AGENT_REASONING_MODE=off`로 유지한다. `assist`를 설정하면 구현된 추론 경로를 사용한다. 운영 기본 적용 여부는 실제 장애 자료에서의 효과와 오탐, 추론 적용률까지 검토하여 결정해야 한다.

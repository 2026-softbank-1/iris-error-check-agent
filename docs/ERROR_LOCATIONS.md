# 문법·컴파일·런타임 오류 위치 분석

작성일: 2026-10-04. `POST /diagnose`의 입력과 `diagnosis-result.v3` 출력 필드는 유지한다.

기존 사전 조회는 Node ENOENT와 제한된 Docker COPY 추론 중심이었다. 이번 확장은 로그에서 보고된 파일·행·열을 공통으로 추출하고 같은 프로젝트의 실제 소스 문맥을 먼저 준비한다. 위치 선택을 위해 LLM을 한 번 더 호출하지 않는다.

## 처리 흐름

1. 기존 정규화·마스킹·EV 부여를 적용한다.
2. 같은 `source_id/stage/stream` 안에서 오류 메시지와 파일 위치를 연결한다. 명시된 진단 위치와 호출 스택 위치를 구분한다.
3. 상대 경로 또는 알려진 컨테이너 루트(`/app/`, `/usr/src/app/`, `/workspace/`)를 프로젝트 경로로 변환한다. `rootDirectory`를 유지하고 실제 제공된 파일 이름과 정확히 대조한다.
4. 최대 3개 파일의 보고 위치 앞뒤 8줄을 기본으로 선택한다. 같은 파일의 가까운 위치는 최대 60줄 창으로 합친다. 멀리 떨어진 위치를 무제한으로 합치지 않는다.
5. 읽은 줄에 기존 SC를 부여하고 원본 로그, 오류 위치 힌트, 소스를 LLM에 제공한다. 원인·반대 근거·해결안을 함께 분석한다.
6. 기존 스키마·EV/SC·후보·파일·줄 범위·수정안 검증 후 동일한 v3 결과를 반환한다.

`src/app.ts(150,7): error TS1005: ';' expected.`가 있으면 파일 앞부분 대신 142–158행을 먼저 읽는다. 파서가 150행에서 멈췄더라도 실제 누락이 앞선 줄에 있을 수 있으므로 LLM은 주변 코드와 대조해야 한다. JavaScript의 유효한 세미콜론 생략을 일괄 오류로 판단하지 않는다.

## 인식하는 로그 형식

| 형식 | 예시 | 처리 |
| --- | --- | --- |
| TypeScript·C# | `src/app.ts(150,7): error TS1005: ...` | 파일·행·열·오류 코드 |
| GCC/Clang·Go·esbuild 계열 | `src/main.c:9:12: error: ...`, `main.go:24:5: undefined: ...` | 같은 줄의 오류와 위치 |
| Node 문법 오류 | 파일`:행` → 코드·caret → `SyntaxError` | 오류 앞의 위치와 예외 EV 연결 |
| Node 일반 예외 | `TypeError` → `at ... (파일:행:열)` | 예외 뒤의 호출 위치 |
| Python 문법·런타임 | `File "...", line N` → `SyntaxError`/`ValueError` 등 | 문법 진단 또는 가장 안쪽 traceback부터 선택 |
| Rust | `error[E0308]` → `--> src/main.rs:16:5` | 오류 코드와 위치 연결 |
| Go panic | `panic:` → 함수 → `파일:행 +0x...` | panic과 스택 위치 연결 |
| ESLint stylish | 파일 제목 → `행:열 error ...` | 파일 제목과 오류 행 모두 EV 보존 |
| Webpack | `ERROR in ./src/App.tsx 7:8` | 오류 위치와 파일 연결 |
| 셸 구문 오류 | `/app/scripts/start.sh: line 9: syntax error ...` | 파일·행 |

지원 형식에 맞는 다른 확장자의 위치도 읽을 수 있지만 위 언어 전체의 모든 진단 형식을 지원한다는 뜻은 아니다. ISO 시각, `#12 3.521`, `npm ERR!`, `[ERROR]`, `[startup-error]` 접두사는 제한적으로 처리한다. 열 번호가 없으면 null로 두며 caret에서 임의로 생성하지 않는다. Windows 경로도 알려진 루트에 매핑되는 경우만 처리한다.

## 모드와 호출 수

| 모드 | 일반 오류 |
| --- | --- |
| `standard` | 로그 단계에 위치 힌트 제공. 소스가 필요하다고 판단했으나 파일을 선택하지 못하면 추출 위치로 범위 보완. 기존 1–2회 호출 유지 |
| `adaptive` | 지원 위치와 소스·예산이 있으면 소스 우선 1회. 없으면 로그 우선 경로 |
| `graph_compact` | 일반 오류는 소스 우선 1회 상세 분석. 기존 지원 ENOENT에만 파일 읽기·배포 그래프와 짧은 판단 프로토콜 적용 |

새 환경변수나 백엔드 필드는 없다. 서버가 이미 `graph_compact`이면 새 코드를 배포한 뒤 일반 오류에도 적용된다. 기본 `standard`는 유지한다. 일반 경로는 상세 응답을 생성하므로 기존 compact 실험의 3–5초 성능을 보장하지 않는다.

## 제한과 실패 처리

- 원본 로그는 생략하지 않는다. 내부 위치 힌트는 최대 12개·3 KiB이며 기존 전체 프롬프트 예산을 넘기면 생략한다.
- 파일당 64 KiB, 선택 SC 합계 8 KiB 등 기존 제한을 유지한다. 일반 경로는 전체 파일 120줄 제한 대신 오류 주변만 선택한다.
- 알려진 경로 안의 정확한 파일만 읽는다. 파일명 유사도·basename 검색, 저장소 밖 접근, URL·사용자 코드 실행은 하지 않는다. 의존성·생성 코드·비밀 파일은 제외한다.
- 다른 출처의 예외와 스택은 연결하지 않는다. 경고·메모·일반 파일 언급만으로 위치를 만들지 않는다. 복구·예상 테스트 신호가 있으면 자동 소스 사전 조회를 보류하고 로그 분석에 맡긴다.
- 보고 줄이 실제 파일 범위 밖이면 일반적으로 사전 조회를 보류한다. 명시된 문법·컴파일 진단이 마지막 줄 다음 EOF를 가리키면 실제 끝 줄까지만 읽고 한계를 남긴다. 없는 줄의 SC는 만들지 않는다.
- 일부 파일 누락·제외는 한계에 남긴다. 전부 읽지 못하거나 예산을 넘으면 기존 로그 우선 경로로 전환한다. 다운로드 오류는 같은 진단에서 캐시하며 반복 다운로드하지 않는다.
- 소스 우선 모델 호출이 실패하면 기존 실패·시간 초과 규격을 반환한다. 유효한 첫 로그 진단 뒤 소스 분석이 실패한 경우에는 기존처럼 첫 진단을 보존한다.
- 추출된 위치는 도구가 보고한 지점이다. 실제 원인·수정 위치, 배포 커밋 일치, 생성 코드의 원본 위치를 확정하지 않는다.
- 언어별 파서·컴파일러로 전체 저장소나 수정 코드를 재검사하는 기능은 이번 범위에 포함되지 않는다. 실제 모델의 원인·수정안 품질은 별도 평가해야 한다.

## 구현과 검증

- `src/ai_error_check_agent/error_locations.py`: 위치·오류 EV 연결, 경로 정규화, 범위 선택, 예산 내 힌트.
- `src/ai_error_check_agent/source_analysis.py`: 세 모드 연동, 일반 소스 우선 경로, 기존 응답 조립·검증.
- `tests/test_error_locations.py`: 지원 형식, Python 실제 파서 출력, 경고·복구·출처 분리, 긴 파일·범위·예산·경로 방어, S3 프로젝트 범위, 모의 모델/API 통합.
- `tests/test_diagnosis_routing.py`: 기존 ENOENT 회귀와 일반 EACCES 위치 경로.

```sh
python -m pytest -q
python -m ruff check src tests evaluation
```

통합 테스트의 모델은 모의 응답이다. Python 파서 사례는 고정 테스트 문자열의 `compile()` 오류를 추출하며 코드를 실행하지 않는다. 테스트 통과를 실제 LLM 진단 정확도나 배포 복구 성공률로 표현하지 않는다. 기존 정량 그래프는 이전 버전 측정이며 이번 변경의 재측정 결과가 아니다.

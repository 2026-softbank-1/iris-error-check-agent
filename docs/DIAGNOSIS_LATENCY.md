# 진단 지연 최적화

백엔드 요청 및 `diagnosis-result.v3` 응답 규격을 유지하면서, 명확한 오류에서 상세 진단을 두 번 생성하는 비용을 줄입니다. 10초는 측정 목표이며 강제 종료 시한이 아닙니다. 모델, 추론 노력, 출력 토큰 한도, 근거 검증, 조건부 수정·검증·되돌리기 요구사항은 유지합니다.

## 서버 설정

```dotenv
AGENT_DIAGNOSIS_MODE=adaptive
```

서버를 재시작하면 적용됩니다. `standard` 또는 미설정은 기존 로그 우선 방식입니다. 운영에서는 환경변수로 설정하고, 문제가 있으면 `standard`로 바꿔 재시작합니다. 프론트엔드·백엔드의 요청 필드나 모델 선택 쿼리는 바꾸지 않습니다. 로컬 CLI의 v2 진단과 대화형 OpenCode 화면은 이 API 경로 설정의 대상이 아닙니다.

OpenAI 처리 티어는 독립적인 설정입니다.

```dotenv
OPENAI_SERVICE_TIER=fast
```

Fast는 추가 비용이 발생하며 계정·모델 지원과 실제 응답 티어를 확인해야 합니다. 미설정은 기존 프로젝트 기본 티어입니다. 일반 티어 결과와 Fast 결과를 하나의 속도 지표로 합치지 않습니다.

## 경로 선택

| 조건 | 동작 |
| --- | --- |
| `standard` | 로그 진단 1회 → 필요하면 소스 조회 및 상세 진단 1회 |
| `adaptive`, 명확한 Node ENOENT 스택과 충분한 소스 | 소스 사전 조회 → 로그+소스로 최종 진단 1회 |
| `adaptive` / `graph_compact`, 지원 문법·컴파일·일반 예외 위치 | 같은 프로젝트의 오류 주변 소스 → 상세 진단 1회. 일반 오류에는 Docker·compact 판단을 추가하지 않음 |
| 회복 신호, 미지원 로그 형식, 모호한 경로 | 기존 로그 우선 경로 |
| 관련 파일 누락·범위 초과·크기 초과·간접 파일 접근 | 기존 로그 우선 경로 |
| 사전 다운로드 실패 | 로그 우선 경로; 같은 요청에서 실패한 다운로드를 반복하지 않음 |

2026-10-04부터 문법·컴파일·일반 예외의 보고 위치도 사전 조회합니다. 지원 로그 형식과 범위는 [ERROR_LOCATIONS](ERROR_LOCATIONS.md)에 정리했습니다. 최대 3개 파일에서 오류 앞뒤 8줄을 기본으로 선택하므로 120줄을 넘는 파일도 제한된 주변 코드로 분석할 수 있습니다. 서로 다른 출처의 예외와 스택은 연결하지 않으며 모든 원본 로그를 모델에 유지합니다.

기존 파일 읽기 전용 경로는 `Error: ENOENT: no such file or directory, open '…'`와 Node 스택을 대상으로 합니다. 같은 누락 경로와 같은 첫 애플리케이션 파일·줄을 가리키는 반복 오류만 허용합니다. 경로는 제공된 소스 스냅샷 또는 해당 프로젝트의 S3 아카이브 안에서만 조회합니다. 컨테이너의 `/app/`, `/usr/src/app/`, `/workspace/` 또는 명시된 상대 경로를 사용하며, 파일명만 비슷한 다른 파일을 추측해 읽지 않습니다.

첫 애플리케이션 파일 전체가 120줄 이하이고 `readFileSync` 호출이 있으며, 코드 근거 8 KiB 및 전체 프롬프트 예산을 만족해야 합니다. 모든 로그를 그대로 LLM에 전달합니다. 원인 판정은 LLM이 수행하며, 선택 규칙은 파일을 고르는 데만 쓰입니다. 다른 호출자 파일·배포 설정·마운트는 미확인으로 남깁니다. 이 제한 때문에 모든 배포 장애가 한 번 호출로 처리되지는 않습니다.

## 품질 보존과 한계

- `EV`, `SC`, `H` ID와 코드 경로·줄 번호의 기존 검증을 그대로 적용합니다.
- 출력 토큰을 강제로 줄이거나 모델을 바꾸지 않습니다. 설명의 중복과 불필요한 항목 수를 줄이는 프롬프트를 사용합니다. 여러 원인·회복·반대 근거가 있으면 항목을 확장합니다.
- 소스 선택은 원인 확정이 아닙니다. 파일이 없는 이유, 실제 배포 커밋, 파일 소유·영속성 계약을 모르면 그 불확실성과 필요한 자료를 남깁니다.
- 소스·로그의 마스킹, URL 허용 범위, 아카이브 크기·경로 검증을 유지합니다. 로컬 파일 접근이나 자동 수정은 추가하지 않습니다.
- 아카이브 캐시는 인증된 진단 요청 하나의 수명 안에서만 존재합니다. 요청·사용자·프로젝트 사이에 공유하지 않습니다. 사전 조회 후 기존 경로로 돌아갈 때 같은 압축 데이터를 재사용하며, 범위가 바뀌면 아카이브 읽기는 다시 수행할 수 있습니다.
- 소스 우선 호출 자체가 실패하면 기존 모델 오류 형태를 반환합니다. 추가 호출을 무조건 붙여 오류를 감추거나 검증되지 않은 결과를 반환하지 않습니다. 로그 우선 경로는 기존처럼 두 번째 호출 실패 시 유효한 첫 진단을 유지합니다.
- `AGENT_KG_MODE`와 `AGENT_REASONING_MODE`는 독립적입니다. 한 번 호출 경로에서는 `source` 단계 기록과 추론 입력을 사용하고 기존 SHACL 규격을 유지합니다.

형식 검증 통과와 합성 사례의 상태 일치는 실제 장애 정확도와 다릅니다. 적용 전후 원인 판정, 반대 근거, 불확실성, 수정의 적용 조건, 검증·되돌리기, 한국어 설명을 함께 검토해야 합니다.

## 서버에서 병목 확인

서버 시작 시 INFO 로그로 다음 측정 기록을 남깁니다. 요청 로그·소스 본문·API 키·presigned URL은 측정 로그에 넣지 않습니다.

- `diagnosis_timing`: 진단 ID, 모드, 경로 선택 사유, 전체 시간, 단계별 시간, 제공자 호출 수, 소스 다운로드·아카이브 읽기 누적 시간.
- `diagnosis_stage_timing`: 단계별 모델 호출 시간과 JSON/근거 검증 시간. 모델 호출 시간에는 네트워크와 제공자 처리가 함께 포함됩니다.
- `openai_service_tier`: 요청한 티어와 제공자가 보고한 실제 티어. 응답에 없는 경우 `unknown`.

공개 응답의 기존 `execution.elapsed_ms`, `execution.stages`, `provider_call_count`, `tokens`도 비교할 수 있습니다. 모델의 첫 토큰 시간이나 네트워크 전송·모델 내부 처리 시간을 각각 분리 측정하는 것은 아닙니다. 실제 서비스의 전체 대기 시간에는 백엔드 조회·HTTP 전송·프론트 폴링 시간이 추가될 수 있습니다.

## 재현 방법

모의 응답 기반 경로·계약 테스트:

```sh
PYTHONPATH=src python -m pytest tests/test_diagnosis_routing.py -q
```

실제 LLM 비교는 API 사용량이 발생합니다. 아래 기본 실행은 3개 사례 × 2개 모드, 진단당 최대 2회 호출로 제한됩니다. S3는 고정 fixture이므로 운영 S3 다운로드 지연을 측정하지 않습니다. 기존 결과 덮어쓰기를 막기 위해 매번 새 출력 디렉터리를 사용합니다.

```sh
PYTHONPATH=src python evaluation/benchmark_adaptive.py --live \
  --env-file .env --output-dir results/adaptive-comparison
```

Fast 티어의 한 사례만 확인하려면:

```sh
PYTHONPATH=src python evaluation/benchmark_adaptive.py --live \
  --env-file .env --output-dir results/adaptive-fast \
  --limit 1 --modes adaptive --service-tier fast
```

`evaluation/adaptive_smoke.v1.json`은 테스트 웹 프로젝트 소스와 파일 누락·동일 출처 회복·다른 출처 정상 로그 사례를 포함합니다. `summary.json`의 상태 일치·한국어 여부는 좁은 자동 점검입니다. 각 결과와 데이터셋의 `review` 기준을 비교해 의미 품질을 별도로 기록해야 합니다. 소수 사례의 평균·최댓값을 운영 p95 또는 정확도 향상으로 표현하지 않습니다.

## 2026-10-03 실측과 적용 판단

동일 `gpt-6.1-sol`, reasoning `low`, 출력 한도 4096으로 로컬 API를 호출했습니다. 소스는 테스트 웹 프로젝트의 3개 파일을 담은 모의 S3 아카이브이며 실제 배포 서버 측정이 아닙니다.

| 파일 누락 사례 | 시간 | LLM 호출 | 출력 토큰(추론 포함) | 검토 결과 |
| --- | ---: | ---: | ---: | --- |
| 기존 standard / 실제 default 티어 | 70.591초 | 2 | 4,203 | 원인·불확실성·조건부 해결안 확인 |
| 초기 adaptive / 실제 default 티어 | 32.237초 | 1 | 1,834 | 중국어 출력으로 품질 실패; 이 프롬프트는 채택하지 않음 |
| 최종 adaptive / 실제 fast 티어 | 22.739초 | 1 | 1,839 | 한국어·근거·불확실성·조건부 수정·검증·되돌리기 확인 |

최종 조합은 이 한 번의 비교에서 약 68% 짧았습니다. 경로, 프롬프트, 처리 티어가 함께 달라졌으므로 각 요인의 독립 효과로 해석하지 않습니다. **10초 목표는 달성하지 못했습니다.** 소수 호출로 p95·실제 장애 정확도·품질 동등성을 보장할 수 없습니다. Fast만 설정해도 항상 10초가 된다는 의미가 아닙니다.

초기 프롬프트의 대조 사례에서는 동일 출처의 회복을 두 모드 모두 `no_failure_evidence`로 판정하고 수정 계획을 만들지 않았습니다(기존 16.769초, adaptive 15.955초). 다른 출처의 정상 로그는 실패 앱의 회복으로 오인하지 않았습니다(기존 80.031초, adaptive 65.954초, 각각 2회 호출). 이 결과는 언어와 항목 수 지시를 보강하기 **전**의 결과이며, 최종 프롬프트 전체에 대한 정확도 검증으로 합산하지 않습니다.

최종 Fast 결과는 원인을 ENOENT와 읽기 코드 범위로 제한하고 패키징·마운트·공급 시점을 구분할 자료를 요청했습니다. 승인된 원본 사용, 기존 파일 덮어쓰기 방지, 데이터 형식 검사, 재기동 후 상태·기능 확인, 기존 데이터 보존 및 롤백 조건을 포함했습니다. 초기안은 언어 지시 위반을 발견해 마지막 지시에서 한국어 사용을 재강조했습니다. 언어 준수도 확률적이므로 실제 장애 표본을 통한 지속 평가가 필요합니다.

검증: 기존 367개 테스트에 경로·예산·취소·S3 재사용·계약·마스킹·그래프 관련 28개 테스트를 추가했습니다. 공개 스키마는 변경하지 않았습니다. 실제 호출 결과의 형식 및 EV/SC/H 참조 검증은 기존 검증기를 통과해야 성공으로 처리합니다. 의미 검토는 이 작업을 수행한 에이전트의 점검이며 독립적인 사람 평가나 블라인드 정확도 실험은 아닙니다.

권장 적용은 `AGENT_DIAGNOSIS_MODE=adaptive`부터 시작해 배포 서버 로그에서 경로와 시간을 확인하는 것입니다. Fast의 추가 비용이 허용되는 서버에서만 티어를 함께 켭니다. 10초를 엄격하게 보장하려면 더 빠른 모델 또는 응답 범위 축소를 별도 비교해야 하며, 이번 변경에서는 품질 검증 없이 이를 적용하지 않았습니다. 운영에 적용하려면 이미지 반영과 서버 환경변수 설정·재시작이 필요합니다.
